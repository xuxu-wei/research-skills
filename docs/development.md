# 开发与人工验证

唯一技能源是 `research-skills-openai/skills/`。修改 Skill 时使用 `skill-creator`；调整插件结构或安装流程时使用 `plugin-creator`。仓库不维护自己的插件管理器或运行时。

## 开发

默认直接在 `main` 上修改源码和按需参考资料，同步 README 中的入口说明。只有用户明确要求时才创建其他分支。影响安装后行为的变更更新插件 Manifest 的 SemVer；版本号只维护在该 Manifest 中。

保留主流程和独立科学评审的职责区分。优先减少重复约束；只有能帮助科学判断或完成任务的细节才进入 Skill。常规写作、搜索、排版和工具选择由 agent 结合上下文决定。

使用 Python 3.11 或更新版本运行辅助脚本，无需安装第三方依赖：

```powershell
python -m unittest discover -s tests/scripts -v
python scripts/auxiliary/generate_flatten_skills.py --output .local/exports/manual-check
```

导出目标必须不存在或为空。更多用法见 [README](../README.md#辅助脚本生成兼容技能包)。

必要时使用本机 `skill-creator` 的 `quick_validate.py` 和 `plugin-creator` 的 `validate_plugin.py` 做格式检查。它们是外部官方工具，不复制进本仓库，也不进入本项目 CI。格式检查不能证明科学质量或实际运行成功。

## 本地安装

通过当前环境的 `plugin-creator` 流程建立或更新本地插件入口，确认其指向正在测试的本地源码。不要把仓库的 GitHub Marketplace 注册误当作本地源码安装；仓库条目仍跟踪 GitHub 的 `main`。

按照该工具提供的安装流程处理本地缓存版本和重新安装，不手工修改个人 Marketplace、配置文件或缓存。测试时确认启用的插件来源，避免本地和 GitHub 副本同时生效。开启新任务后再验证；本地缓存版本后缀不提交到源码。

## 人工验证

所有者在实际加载新版本的新任务中选择适合当前变更的输入，观察结果并判断质量。不要因为一次纯格式修改而重复全部场景。维护中的能力包括：

| 场景 | 人工观察重点 |
| --- | --- |
| 通用学术写作 | 从材料建立连贯论述，读者能够理解对象、问题、做法与判断，文体和专业程度合适 |
| 学术编辑 | 先解决结构和衔接，再处理措辞；事实、证据、必要限定和作者立场保持稳定 |
| 选题 | 问题与贡献清楚，证据支持充分，方法与资源可行，选项之间有实质差异 |
| 标书 | 背景论证、目标、方法和工作计划相互支持，关键承诺有依据 |
| 论文 | 忠实于实际方法和结果，正文与表图一致，结论不过度延伸 |
| Perspective | 有明确论点、合理推理和有力反论证，体现学术贡献 |
| 已有研究改进 | 区分已完成研究与拟补充工作，科学收益、成本和依赖清楚 |
| 方法学预检 | 找出真正影响推断的问题，建议与研究类型相称 |
| 医学期刊评审 | 临床意义、方法有效性和期刊适配分别有依据 |
| SAP 编写与评审 | 目标、估计量、数据和方法一致，重要分析决策可执行且透明 |

在主流程中同时观察评审是否独立、重大修订是否得到新评审，以及异议和未解决问题是否留给研究者。补充检查关键证据不足、评审不可用、用户中途改变方向等实际遇到的情况；有用草稿应能保留，限制应准确说明。

### 学术写作与编辑的人工检查

两份新技能的正文和参考说明使用中文，便于所有者直接审阅。行为验证可选用参考资料中的情境或自己的材料，关注实际理解与内容忠实，不逐字匹配示例答案：

- 用分析计划检查方法、结局和缺失处理是否便于一起理解，含糊术语和科学冲突是否被明确指出。请不了解此前聊天的读者复述对象、比较和分析顺序。
- 用教材检查重复辩解是否减少，必要的否定、公式条件、算法、题义和答案是否保留。
- 用中英文及不同学科材料检查专业程度、引文和结论强度；编辑英文稿时观察是否保持英文，除非任务要求翻译。
- 在独立学术任务中分别尝试自动匹配与显式调用；在现有研究流程中观察起草和成稿编辑是否使用两个技能，并由原任务完成。
- 用评审报告检查批评程度、依据和异议是否完整；只检查的请求应得到建议，不应改写文件。

这两份技能的写作或编辑自查不计作独立科学评审，也不计作所有者人工验收。实际行为结果尚未观察时，保留 ROADMAP 中的待办状态。

用简短自然语言记录所用源码版本、任务或产物位置、实际发现和所有者结论即可。个人输入和运行记录放在 `.local/research-runs/`。在 [唯一 ROADMAP](../ROADMAP.md) 更新验证状态，避免把旧版本测试结果当成新版本证据。

## 自动测试范围

`tests/scripts/` 使用合成目录和文件测试辅助脚本的复制行为、输出路径、覆盖保护、资源过滤和失败回滚。不测试 Skill 的措辞、固定标题、评分门槛、角色数量或研究产物，也不自动调用 LLM。

GitHub Actions 保留检查名 `OpenAI Plugin Preview / validate`，对 `main`、`codex/**` 分支和 Pull Request 运行脚本测试。检查通过只代表辅助脚本通过测试。

## 交付

审阅差异并分批提交，推送到 GitHub 的 `main` 并检查脚本 CI。人工验证完成后，由所有者决定是否发布。推送、CI 通过和更新版本号都不等同于人工验收或发布完成。

合入 `main` 后，可按 README 的 GitHub 更新命令安装，再开新任务检查实际加载的版本。如果需要回退，从 Git 历史选择已知可用版本，通过正常插件安装流程处理；不维护另一套长期技能源或生成副本。
