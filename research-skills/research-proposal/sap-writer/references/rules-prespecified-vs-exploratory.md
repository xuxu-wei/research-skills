# Prespecified vs Post Hoc and Exploratory Analysis Rules

## Analysis classes

### Prespecified confirmatory analysis

Defined before outcome/result inspection and tied to the primary objective or formal secondary objective.

Required fields:
- hypothesis or estimand;
- endpoint/outcome;
- analysis population;
- model or method;
- effect measure, contrast, or metric;
- alpha level or interval estimation plan when applicable;
- multiplicity handling when multiple confirmatory claims exist;
- decision or interpretation rule.

### Prespecified supportive or secondary analysis

Defined before result inspection but not the primary basis for the main conclusion.

Required fields:
- objective;
- method;
- relationship to primary analysis;
- whether confirmatory or descriptive/supportive;
- multiplicity and interpretation rule.

### Post hoc analysis

Added after seeing feasibility, data quality, distributions, protocol deviations, or results.

Required fields:
- trigger/source;
- whether it was data-quality driven, feasibility driven, reviewer requested, or result driven;
- method;
- why it is needed;
- interpretation limit;
- whether it requires future confirmation.

### Exploratory analysis

Used for hypothesis generation, signal detection, mechanism exploration, or descriptive learning.

Required fields:
- rationale;
- planned output;
- method;
- no-confirmatory-claim statement;
- future validation or confirmatory route, if applicable.

## Rules

- Never mix prespecified and post hoc analyses in the same section without labels.
- Do not use exploratory analyses to rescue a failed primary analysis.
- Do not state exploratory P values as confirmatory evidence.
- If the SAP is written after data inspection, explicitly state which analyses were prespecified by protocol and which are data-driven.
- If prespecification status is unknown, mark it as an unresolved SAP issue.
- Analysis changes made after data review must appear in the change summary.
